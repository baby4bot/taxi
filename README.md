## 📖 โปรแกรมนี้คืออะไร

เว็บแอปหน้าเดียว (Single-file Web App) ที่เปลี่ยนมือถือให้เป็น **มิเตอร์แท็กซี่** สำหรับคนขับ
ใช้งานบนหน้ารถจริง — ค้นหาปลายทาง → ประเมินราคาและระยะทาง → นำทาง → จับเวลามิเตอร์
→ ออกใบเสร็จให้ผู้โดยสาร พร้อมระบบสมาชิก/สิทธิ์สำหรับสหกรณ์หรือกลุ่มคนขับ

ออกแบบมาให้ **เปิดค้างไว้ตอนขับได้จริง**: จอเต็ม, ตัวอักษรใหญ่, ปุ่มกดง่าย,
ทำงานต่อได้แม้สลับไปใช้ Google Maps หรือปิดแอปไปแล้ว

## ✨ ฟีเจอร์หลัก

### 🚕 ฝั่งคนขับ (ใช้งานหน้ารถ)

- 🧮 **คำนวณค่าโดยสารอัตราก้าวหน้า** — กรอกระยะทางเอง หรือให้ระบบดึงระยะจากเส้นทางจริง
  เลือกได้ว่าขับ **รถปกติ (35฿)** หรือ **แวน (40฿)**
- 🔍 **ค้นหาปลายทางแล้วประเมินทันที** — ได้ทั้งระยะทาง / เวลา / ราคา / เวลาถึงโดยประมาณ
  (ใช้ **TomTom Search + Routing** ที่คิดเวลารถติดจริง ไม่ใช่แค่ระยะเส้นตรง)
- 📍 **หน้าสรุปเส้นทางก่อนเริ่ม** — ตรวจปลายทางให้ชัดก่อนกดเริ่ม ไม่กดผิดที่
- ▶️ **จับเวลามิเตอร์ (Meter)** — เปิดแล้วนับ **เวลาวิ่ง / เวลารถติด / ระยะทางที่วิ่งจริง** จาก GPS
  มีปุ่ม **หยุดชั่วคราว** และปุ่ม **จบเที่ยว**
- 🧭 **ปุ่มนำทาง Google Maps ในตัว** — ส่งต่อจุดหมายให้ Google Maps นำทางด้วยคำสั่งเดียว
  (คนขับใช้ Google Maps นำทางไปได้เลย แล้วกลับมาเข้าแอป มิเตอร์ยังนับต่อ)
- 🗺️ **แผนที่นำทางขนาดย่อ (Mini Map)** — แผนที่ลอยอยู่มุมจอที่โชว์ **ตำแหน่งรถบนเส้นทาง** แบบที่เห็นใน Google Maps:
  แผนที่โหมดมืดอ่านง่าย · เส้นทางสีน้ำเงิน (ช่วงที่วิ่งผ่านแล้วเป็นสีจาง) · หมุดจุดหมาย · หัวรถเป็นลูกศรหมุนตามทิศที่วิ่งจริง ·
  เลื่อนตามรถเองอัตโนมัติ พร้อมบอก **ระยะทางที่เหลือ + เวลาถึงโดยประมาณ** และแถบความคืบหน้าของเที่ยว ·
  **บอกจุดเลี้ยวถัดไป** — ไอคอนลูกศรบอกทิศ (เลี้ยวซ้าย/ขวา · หัก · ชิด · กลับรถ) + ระยะถึงจุดเลี้ยว และจุดหมุดบนเส้นทาง
  (คำนวณจากรูปทรงเส้นทางเอง จึงใช้ได้กับเที่ยวที่กู้คืนมาด้วย) — เลยจุดเลี้ยวสุดท้ายแล้วจะเป็น "ตรงไปจนถึงจุดหมาย" ·
  **เตือนล่วงหน้าด้วยเสียง + สั่น + เสียงพูดไทย** — ไกล ~300 ม. (2 จังหวะนุ่ม ๆ) และใกล้ ~80 ม. (3 จังหวะถี่กว่า) เตือนระดับละครั้งเดียวต่อจุดเลี้ยว
  (จอดติดอยู่ตรงนั้นก็ไม่ดังซ้ำ) · เคารพสวิตช์ปิดเสียง/ปิดสั่นในหน้าโปรไฟล์ · ซ่อน Mini Map = เงียบ ·
  **🔊 เสียงนำทางพูดภาษาไทย (15 ก.ย. 2569)** — พูดบอกก่อนถึงจุดเลี้ยว ไม่ต้องละสายตาจากถนน:
  • ไกล ~300 ม. → **“อีก 300 เมตร เลี้ยวซ้าย”** (บอกทั้งระยะและท่า · ปัดระยะให้พูดลื่น เช่น 250/300/1.2 กิโลเมตร)
  • ใกล้ ~80 ม. → **พูดแต่ชื่อท่า** (“เลี้ยวขวา”) เหมาะกับจังหวะต้องตัดสินใจ
  • ทำงาน **คู่กับ** เสียงติ๊ง/สั่นเดิม ไม่แทนกัน: เสียงติ๊งดังก่อน 320 มิลลิวินาที แล้วตามด้วยคำพูด (ไม่ทับกัน)
    · ถ้าใกล้ถึงท่าก่อนที่คำบอกระยะจะพูดจบ → คำสั่งที่มีความสำคัญกว่าจะ **ตัดคิวก่อนหน้า** แล้วพูดทันที
  • เปิด/ปิดได้เอง 2 ระดับ: **หน้าโปรไฟล์ → “เสียงนำทางพูด (ภาษาไทย)”** (ค่าประจำบัญชี ใช้ทุกเครื่อง)
    และ **ปุ่ม 🔊 บน Mini Map** (ปุ่มลัดตอนขับ — จำเฉพาะเครื่องนั้น)
  • ตรวจเร็ว ๆ : `window.navVoiceDebug()` (รองรับไหม · มีเสียงไทยไหม · พูดอะไรไปแล้ว) · ลองพูดทันที: `navVoiceTest()`

  **🚦 ชั้นข้อมูลจราจรบน Mini Map — ❌ เอาออกแล้ว (15 ก.ย. 2569 เพราะกินโควตา):**
  • เคยมีชั้นเส้นสีจราจร (TomTom Traffic Flow) ทับบนแผนที่ + ปุ่ม 🚦 มุมล่างซ้าย
  • **ทำไมเอาออก:** กระเบื้องจราจรนับเป็น **คำขอต่อคีย์ TomTom ทุกใบ** ที่โหลด (ต่างจากกระเบื้อง OSM ที่ฟรี)
    → กินโควตาที่ต้องเก็บไว้ใช้กับส่วนจำเป็นจริง ๆ (Search/Routing ที่คิดเวลารถติด)
  • ตอนนี้ Mini Map เหลือ: กระเบื้อง **OpenStreetMap** (ฟรี) + เส้นทาง + รถ + จุดเลี้ยว — **โควตา TomTom ถูกใช้เฉพาะตอนคำนวณเส้นทางเท่านั้น**
  • **รถติดดูได้จากอะไร:** ตัวเลข “รถติด” บนมิเตอร์ (มาจาก GPS + โมเดลช่วงปิดแอป) ซึ่งเป็นค่าที่ใช้คิดเงินจริงอยู๋แล้ว
  • ⛔ ห้ามใส่กลับโดยไม่ถามคนขับก่อน · ถ้าจำเป็นจริงให้ใช้บริการจราจรแบบไม่กินโควตา (เช่น OSM-based) แทน

  **🔍 ซูมเข้าเองก่อนถึงทางแยก แล้วถอยออกหลังผ่าน — เหมือน Google Maps (15 ก.ย. 2569):**
  • บังคับไม่ได้เลยว่าต้องคอยหมุนล้อ/หุบนิ้วเอง: แผนที่ **ค่อย ๆ ซูมเข้า** เมื่อรถเข้าใกล้จุดเลี้ยวถัดไป แล้ว **ถอยออกเอง** หลังผ่านแยก
  • ค่อยเป็นค่อยไปทุกเฟรม (ไม่กระโดดเป็นขั้น): ไกลแยก → ซูมตามความเร็วเป็นปกติ · ≤ 320 ม. → เร่งนิดเดียว · ≤ 200 ม. → เร่งครึ่งระดับ · ≤ 60 ม. → ซูมสุด
  • **ค้างซูมไว้ที่ตัวแยก** จนรถออกห่างเกิน ~60 ม. แล้วค่อยถอยออก (เหมือน Google ที่ยังซูมอยู่ตอนอยู่กลางสี่แยก)
  • **ดูจากจุดเลี้ยวของเส้นทางเอง** — ไม่เรียก API เพิ่ม ไม่กินโควตา (ใช้ข้อมูล `buildTurns` ที่มีอยู่แล้ว)
  • **นิ้วคนขับมาก่อนเสมอ:** พอผู้ใช้หุบนิ้ว/หมุนล้อซูมเอง ระบบจะหยุดปรับอัตโนมัติทันที · กด `◎` กลับมาโหมดตามรถจึงกลับมาซูมเอง
  • เพดานซูม 19 (กันแผนที่ซูมจนอ่านถนนไม่ออก) · ตรวจเร็ว ๆ: `window.navMiniDebug()` → `zoom` · `zoomTarget` · `zoomAuto` · `turnZoomBoost`

  **🎞️ แผนที่ไหลต่อเนื่อง + ลูกศรชี้ขึ้นบนเสมอ — เหมือน Google Maps (16 ก.ย. 2569):**
  • **ตำแหน่ง/ทิศที่วาดไหลตามค่าจริงทุกเฟรม** (ประมาณ 60 เฟรม/วินาที) — เดิมวาดตามพิกัด GPS ตรง ๆ ⇒ แผนที่ขยับ “เป็นจังหวะ”
    (รอ fix ถัดไป) คนขับเห็นเป็น “จุดไม่เคลื่อนที่ตาม” · ไล่ทันแล้วหยุดวาดเอง (จอด/อยู่กับที่ = ไม่กินแบต)
  • **ลูกศรถอยู่ต่ำกว่ากึ่งกลางจอ (70% = จุดยึด)** — เห็นถนนข้างหน้าเยอะขึ้น · ตอนลากเองใช้จุดยึดเดิม ⇒ เริ่มลากแล้วภาพไม่กระโดด
  • **จุดเลื่อนตามแผนที่ (🎈 16 ก.ย. 2569 · ตามที่คนขับขอ)** — ลูกศร **ค่อย ๆ เลื่อนขึ้นจอ** ตามระยะที่วิ่งจริง (ไม่ตรึงอยู่กับที่)
    พอเลื่อนได้ 34% ของความสูงจอ → **กล้องไล่ทัน** ให้ลูกศรกลับมาที่จุดยึด แล้วเริ่มนับใหม่
    · ⚙️ **ไล่ทันด้วยความเร็วคงที่ (16 ก.ย. 2569)** — `crawlCatchMps()` = `navCatch% × ความสูงจอ × เมตร/พิกเซล` (เมตร/วินาที **คงที่** ไม่ใช่เอกซ์โพเนนเชียล)
      ⇒ ออกตัวนุ่มเท่ากันทุกครั้ง และใช้เวลาไล่ทันคงที่ = ช่วง ÷ ความเร็ว (34 ÷ 16 ≈ 2.1 วิ) **ไม่ขึ้นกับระดับซูม** (เดิม `exp(-dt/0.8)` เร่งช่วงแรกแล้วค่อย ๆ หยุด = รู้สึกกระตุก)
    · เพดานคิดเป็น “เมตร” จากระดับซูมจริง ⇒ ซูมเข้าใกล้แยก เพดาน (เมตร) ก็สั้นลงเอง · ตอนจอด/คลาน ≤ 2 กม./ชม. กล้องไม่เลื่อน
    · ลากเอง/กด `◎` = รีเซ็ตจุดกลับจุดยึดทันที (ไม่ค้างเลื่อน) · ตรวจเร็ว: `navMiniDebug()` → `crawlM` · `crawlCatch` · `crawlMaxM` · `crawlCatchMps`
  • **⚙️ แอดมินตั้งค่าได้เอง (16 ก.ย. 2569)** — ตั้งค่าการใช้งาน → **แผนที่นำทาง (Mini Map)**: ช่วงการเลื่อนของจุด 0–45% (0% = ตรึงลูกศรกับที่) · ความเร็วการไล่ทัน 4–40% ของความสูงจอ/วินาที
    · เก็บใน `settings/ui_prefs` (ใช้ `updateMask` → ไม่ทับค่าแถบเลื่อน) + แคชในเครื่อง ⇒ **ทุกเครื่องใช้ค่าเดียวกัน** · ต้องกด **บันทึก** ถึงขึ้นเซิร์ฟเวอร์ (และต้องยืนยันตัวตนก่อน เพราะมีผลกับคนขับทุกคน)
    · เลื่อนสไลเดอร์ = เห็นผลกับ Mini Map ที่เปิดอยู่ทันที (ยังไม่ขึ้นเซิร์ฟเวอร์) · สิทธิ์ที่ต้องมี: `canManageNavMap`
  • **แผนที่หมุนตามรถด้วยอัตราจำกัด 85°/วินาที** — ไม่สะบัดเวลา GPS กระโดด · ตอนเลี้ยวเห็นเส้นทางหมุนตาม ไม่ต้องคอยเทียบเอง
  • 🐞 **แก้ “ทิศไม่หมุนตามรถตอนวิ่งเร็ว”**: เกณฑ์เดิม “ต้องขยับ ≥ 12 ม. ต่อครั้ง” ⇒ ที่ 40 กม./ชม. (GPS 1 ครั้ง/วินาที ได้ ~11 ม.)
    **ทิศไม่เคยอัปเดตเลย** — ตอนนี้อิงจุดอ้างอิงที่ไกล 5–10 ม. (วิ่งช้ากว่านั้นใช้ช่วงสั้นลง) และตอนความเร็ว ≤ 6 กม./ชม. ใช้ทิศของเส้นทางแทน
  • ตรวจเร็ว ๆ: `window.navMiniDebug()` → `dispCar` · `dispHead` · `lagM` · `animating` · `window.navMiniCarScreen()` = ตำแหน่งลูกศรบนจอจริง (ตอนตามรถต้องได้ `[กว้าง/2, สูง×0.7]`)

  **🔇 ปุ่มปิดเสียงบน Mini Map + ย้ายแถบคำบอกเลี้ยวขึ้นบน (15 ก.ย. 2569):**
  • ปุ่ม **🔊/🔇** วงกลมโปร่งใส **มุมล่างขวาของแผนที่** (ก่อนหน้านี้อยู่บนหัวแผนที่) — กดครั้งเดียว = เงียบทั้ง “คำพูด” และ “เสียงติ๊งเตือนจุดเลี้ยว”
    • **ยังสั่นเตือนอยู่** (คนขับที่ชอบโหมดสั่นอย่างเดียวใช้ท่านี้ได้) · ปุ่มติดสีแดง + ไอคอน `volume_off` ให้เห็นชัดว่ากำลังเงียบ
    • กดปิดเสียงขณะมีคำพูดค้างอยู่ = **ตัดเสียงที่พูดอยู่ทันที** · จำค่าไว้ในเครื่อง (`taxi_navmini_v2.muted`)
    • ค่าบัญชี (หน้าโปรไฟล์) คือตัวตัดสินเสมอ: ถ้าปิดเสียงนำทางไว้ในโปรไฟล์ ปุ่มบนแผนที่เปิดก็ไม่ดัง
  • **แถบคำบอกเลี้ยว (“อีก 250 ม. · เลี้ยวขวา”) ย้ายขึ้นไปบนสุด ใต้หัวแผนที่** — ลำดับการ์ดใหม่:
    หัว (ชื่อจุดหมาย + ปุ่ม) → **แถบคำบอกเลี้ยว** → แผนที่ → แถบ “เหลือ กม./นาที/เวลาถึง” + แถบความคืบหน้า
    (ตรงกับจังหวะที่คนขับมอง: เห็นคำสั่งก่อนเห็นแผนที่)
  **ลากย้ายได้ทั้งก้อน** (จำตำแหน่ง/ขนาดไว้) · ย่อ–ขยายได้ 2 ขนาด · ลากแผนที่เอง/หุบนิ้วเพื่อซูม แล้วกด `◎` กลับมาที่รถ ·
  ปุ่ม `✕` ซ่อนได้ — เปิดกลับมาเองทุกครั้งที่เริ่มเที่ยวใหม่หรือกดเริ่มต่อเที่ยวค้าง และปิดเองเมื่อจบเที่ยว
  ปุ่ม `✕` ซ่อนแผนที่แล้ว **เปิดกลับได้ทันทีระหว่างเที่ยว**: มีปุ่ม 🗺️ “เปิดแผนที่นำทาง” โผล่ในแถบ
  “📍 ไปที่: จุดหมาย” ทั้งจอมิเตอร์ปกติและจอมิเตอร์ใหญ่ — กดแล้วแผนที่กลับมาโชว์เส้นทาง/ตำแหน่งรถต่อจากเดิม
  (ปุ่มจะหายเองเมื่อแผนที่กลับมาแสดง หรือเมื่อจบเที่ยว)

  **🗺️ พฤติกรรมใหม่ (15 ก.ย. 2569) — 3 เรื่องที่คนขับขอ:**

  | เรื่อง | เดิม | ตอนนี้ |
  |---|---|---|
  | ตอนเริ่มนำทางจาก “ค้นหาเส้นทาง” | แผนที่เด้งขึ้นเองทันที | **ไม่เด้ง** — มีปุ่ม 🗺️ **สีฟ้า** ในแถบ “📍 ไปที่:” ให้กดเปิดเอง (เดิมปุ่มสีเทา อ่านไม่ออกว่ากดได้) |
  | ทิศของแผนที่ | หันทิศเหนือตาย (มีแต่ลูกศรที่หมุน) | **หันหัวขึ้น (heading-up)** — รถชี้ขึ้นบนเสมอ เส้นทางหมุนตามทิศรถ |
  | แหล่งที่มาของทิศ | รอ GPS ขยับก่อน (ยังไม่ขยับ = ลูกศรชี้ทิศเหนือ = ชี้ผิดทาง) | **ทิศของเส้นทางเอง** เมื่อ GPS บอกทิศไม่ได้ (จอด · เพิ่งเริ่มเที่ยว) — แผนที่หันหัวถูกตั้งแต่วินาทีแรก |
  | ระยะ “เหลือ” ระหว่างวิ่ง | อัปเดตทุกครั้งที่โพเส้นทางใหม่ (ทุก 120 วิ) → เลขค้างเป็นนาที | **อัปเดตทุกวินาที** — snap ตำแหน่งรถบนเส้นทางในเครื่อง (ไม่กินโควตา) |

  - **จำใจคนขับได้**: กดปุ่มเปิดแผนที่เอง → เที่ยวหน้าจะเปิดให้เองอัตโนมัติ · กด ✕ ปิดเอง → เที่ยวหน้ากลับไปเป็น “ไม่เด้ง” (`pref.autoOpen` ใน `taxi_navmini_v2`)
  - **🆕 รีเฟรช/กลับเข้าแอป = คงสถานะเดิม (15 ก.ย. 2569)** — เดิมพอกู้เที่ยวค้างแล้วแผนที่ **เด้งขึ้นเองเสมอ**
    ตอนนี้ถ้ายังไม่ได้กดเปิดเอง แผนที่จะ **ปิดอยู่เหมือนเดิม** (มีปุ่ม 🗺️ ให้กดเปิดเมื่ออยากดู)
  - **🔇 แผนที่ปิด = เงียบทั้งชุด** — คำพูดนำทาง · เสียงติ๊งเตือนจุดเลี้ยว · สั่น จะทำงาน **เฉพาะเมื่อแผนที่เปิดมองอยู่**
    (กันเตือนทั้งที่ไม่มีแผนที่ให้ดู — การโพเส้นทางใหม่ทุก 120 วิ ก็ไม่ทำให้เสียงดังขึ้นมา)
  - **หมุนฉากทั้งบาน** ไม่ใช่หมุนแต่ลูกศร: `ctx.rotate(-bearing)` รอบกลางจอ + ขยายช่วงกระเบื้อง/`clip` เป็นแนวทแยง (`rotPad`, `CLIP_PAD`) ไม่งั้นมุมจอเป็นดำ
  - **ท่าลากต้องแปลงพิกัด**: แผนที่หมุนอยู่ → แปลง delta ของนิ้วเป็นพิกัดแผนที่ก่อน (`bearing` rad) ไม่งั้นลากแล้วแผนที่เลื่อนคนละทางกับนิ้ว
  - **ทิศมาจากไหน (`routeHeadingAt` · `alignHeadingToRoute` · `turnToward`)**:
    ① GPS ขยับ ≥ 12 ม. → ใช้ทิศจากพิกัด (หมุนนุ่ม เพดาน 30°/ครั้ง) ·
    ② จอด/คลานช้า < 6 กม./ชม. → ยึด **ทิศของเส้นทาง** (มองล่วงหน้า ~40 ม. ให้ทิศนิ่ง ไม่สั่นตามจุด GPS) ·
    ③ พิกัดกระโดดไกล > 500 ม. (ตำแหน่งเก่าค้าง/กลับเข้าแอป) → **ไม่ใช้** ทิศจากพิกัด ยึดเส้นทางแทน (ไม่งั้นหัวรถชี้ผิดทาง)
  - **หันหัวถูกตั้งแต่วินาทีแรก**: ตั้งเส้นทาง · เริ่มนำทาง · กลับเข้าเที่ยวค้าง → `alignHeadingToRoute()` หันให้ทันที
    (เดิม `bearing = 0` = ชี้ทิศเหนือ จนกว่ารถจะขยับ — อาการ “ดูเหมือนเป็นแค่เส้นทาง ไม่เหมือนนำทาง”)
  - **กับดัก**: ตัวแปรสถานะของแอปเป็น `let` ระดับสคริปต์ **ไม่ใช่ property ของ `window`** — สคริปต์ทดสอบ/สคริปต์ฉีดที่รันคนละ isolated world จะตั้งค่าไม่ติด (ดู note ใน `.freebuff/run.md`)

### 🚦 ราคาประเมินคิด “เวลารถติด” ด้วย (16 ก.ย. 2569)

เดิมหน้าสรุปเส้นทางคิด **แค่ระยะทาง** ⇒ ประเมินต่ำกว่ามิเตอร์จริงทุกครั้งที่เส้นทางมีรถช้า/รถติด
(เคสจริง: 15.18 กม./32 นาที → ได้ 129 ฿ ทั้งที่ระหว่างนั้นมีเวลาที่มิเตอร์จะคิด)

ตอนนี้ราคาประเมินใช้สูตรเดียวกับมิเตอร์: `ค่าแรก + ปัดคู่((ระยะทาง + เวลารถติด × 3.00/นาที))` + ค่าทางด่วน

| ส่วนของเวลารถติด | ที่มา |
|---|---|
| ช่วงรถติด | ช่วง `TRAFFIC` จาก TomTom (`sectionType=traffic` → `effectiveSpeedInKmh`) — คิดเฉพาะสัดส่วนที่รถคลาน `(m−v)/(m−c)` |
| ไฟแดง/ต่อแถว | `เวลาที่ใช้จริง − เวลาถนนโล่ง − ดีเลย์ที่จัดเป็นช่วงรถติด` × 50% (`PLAN_STOP_SHARE`) |

- แถบสีฟ้าใต้การ์ดราคาบอกที่มาและยอดที่เพิ่มจากเวลาโดยตรง (เช่น “ประมาณเวลารถติด ~5 นาที (ช่วงรถติด 1 น. + ไฟแดง/ต่อแถว 3 น.) → +15 ฿”)
- **โควตาไม่เพิ่ม:** ใช้คำขอ routing เดิม (เพิ่มแค่พารามิเตอร์ `sectionType=traffic` + `computeTravelTimeFor=all`)
- **ไม่กระทบเวลารถติดช่วงล็อกจอ:** `noTrafficTravelTimeInSeconds` ไม่ถูกส่งเข้า gap model (คงเป็น `null` เหมือนเดิม) — ไม่งั้นเวลารถติดช่วงปิดแอปจะขาด
- **ไม่คิดซ้ำ:** ระหว่างเที่ยว (มิเตอร์นับจริงอยู่แล้ว) ราคาประเมินจะกลับไปคิดแบบระยะทาง — ไม่บวกเวลาวางแผนซ้ำ
- ตรวจจริง: 15.26 กม./26 นาที → 129 → **145 ฿** · ทางหลวง 80.7 กม./91 น. → +9 นาที (+28 ฿) · ในเมือง 24 กม. → +9 นาที (+26 ฿)

### 🎨 ระบบธีม (3 โหมด)

- ธีมถูกกำหนดที่แท็ก `<html>` เป็น **คลาสเดียว**: `dark` (ค่าเริ่มต้น) · `oled` (ดำสนิท) · `light` (สว่าง)
- สีทั้งหมดอยู่ใน **CSS Variables** ที่ `:root` และแต่ละธีมมีบล็อกทับสีของตัวเอง (เช่น `html.light { … }`)
  — **ทับเฉพาะชุดสี ไม่แตะเลย์เอาต์/ขนาด** ขนาดปุ่ม ระยะห่าง และตำแหน่งทุกจอจึงเท่ากันทั้ง 3 ธีม
- ตัวคุมอยู่ใน JS: `THEME_ORDER = ['dark','oled','light']` · `applyThemeMode(mode, opts)` ·
  `setThemeMode()` · `cycleThemeMode()` · `syncThemeUi()`
- ปุ่มสลับที่หน้าแรก **วนตามลำดับ** (มืด → ดำ OLED → สว่าง) พร้อมไอคอนบอกโหมด (พระจันทร์ / พระจันทร์มีดาว / ดวงอาทิตย์)
  และในหน้าโปรไฟล์เลือกตรงได้ 3 ปุ่ม
- เก็บค่าที่ **Firestore `users/<uid>.themeMode`** (ซิงก์ข้ามทุกเครื่องของคุณ) + เขียน `oledMode` ควบคู่ไว้ให้บิลด์เก่าอ่าน
  · `localStorage` เป็นสำรองตอนออฟไลน์ · เปลี่ยน `<meta name="theme-color">` ของเบราว์เซอร์ตามธีมด้วย
- **เพิ่มธีมใหม่** = เพิ่มคลาส + บล็อกทับสี แล้วต่อท้าย `THEME_ORDER` — ไม่ต้องแก้โค้ดส่วนอื่น

### 🔐 ล็อกอิน / สมัครด้วยบัญชี Google (เพิ่ม 16 ก.ย. 2569)

ผู้ใช้ใหม่ไม่ต้องตั้งรหัสผ่านก็เข้าได้ — กดปุ่มเดียวจบ และบัญชีเก่ายังใช้รหัสผ่านเดิมได้เหมือนเดิม

**สิ่งที่เห็นบนจอ**

| จุด | พฤติกรรม |
|---|---|
| หน้าเข้าสู่ระบบ → **“ดำเนินการต่อด้วย Google”** | ครั้งแรก = **สร้างบัญชีให้อัตโนมัติ** (ผู้ใช้ทั่วไป) แล้วเข้าสู่ระบบให้เลย · ครั้งต่อไปเข้า **บัญชีเดิม** |
| หน้าโปรไฟล์ → การ์ด **“บัญชี Google (ทางเลือกล็อกอิน)”** | ผูก/ยกเลิกการผูกได้เอง (ยกเลิกต้องยืนยันด้วย PIN) · สถานะอ่านจาก **บัญชีผู้ใช้** จึงเห็นถูกต้องทุกเครื่อง |
| บัญชีเดิมหลังผูก Google | **เข้าได้ 2 ทางเสมอ** — ปุ่ม Google หรือ username/รหัสผ่านเดิม (ระบบไม่ลบรหัสผ่าน) |
| ลูกค้าใหม่ที่สมัครด้วย Google | เด้ง **หน้าต้อนรับ 3 ขั้น** อัตโนมัติ: ชื่อ/ทะเบียนรถ/เบอร์โทร (บังคับ) → ตั้งรหัสผ่าน (ข้ามได้) → สรุป username + วิธีเข้าใช้ 2 ทาง · **ยังไม่ครบ = กดเริ่มมิเตอร์ไม่ได้** |
| บัญชีที่ยังไม่มีรหัสผ่าน | หน้าต่างรหัสผ่านเปลี่ยนเป็น **“ตั้งรหัสผ่าน”** (ไม่ถามรหัสเดิม) |
| ปุ่ม “ผูกบัญชี Google” | ถ้าบัญชีนี้ **ใช้ Google อยู่แล้ว** (สมัคร/ล็อกอินด้วย Google หรือผูกไว้ก่อนหน้า) ปุ่มจะเป็น **สีเทา กดไม่ได้** — และตัวฟังก์ชันก็กันผูกซ้ำด้วย (ไม่ใช่แค่ซ่อนปุ่ม) |
| ยกเลิกการผูก | เห็นปุ่มเฉพาะเมื่อ **รู้ Google uid จริง** และ **มีรหัสผ่านของตัวเองแล้ว** — บัญชีที่สร้างด้วย Google (ยังไม่มีรหัสผ่าน) ไม่โชว์ปุ่ม เพราะยกเลิกแล้วจะเข้าระบบไม่ได้เลย |
| บัญชีถูกระงับ | บล็อกพร้อมข้อความบอกชัด |

**กลไก (อ่านก่อนแก้โค้ด)**

- **uid ของ Google → เอกสาร `authLink/{uid}` = `{ docId, email, linkedAt }`** แล้วทุกอย่างเดินโฟลว์เดิม (`users/{docId}` · PIN · สิทธิ์ · บันทึกการเข้าใช้งาน) — บัญชีเดียวกับระบบ username/รหัสผ่าน ไม่มีระบบคู่ขนาน

| มีผลเมื่อไหร่ | **ทันทีในเครื่องที่กดบันทึก** (อัปเดตแคช `taxi_reserved_words_v1` หลังเขียนสำเร็จ) · เครื่องอื่นได้ตอนเปิดแอปครั้งถัดไป (`__reservedFetch`) · บันทึกทุกครั้งลง **ประวัติความปลอดภัย** และเพิ่มบรรทัดใน **ประวัติเวอร์ชัน** |
| ⚠️ กันพลาด | บันทึกรายการ **ว่าง** = ไม่มีด่านห้ามไอดีเลย (หน้าจอเตือนไว้) · คำ < 2 ตัวอักษร หรือคำซ้ำ ถูกกันตั้งแต่ตอนเพิ่ม · คำถูก normalize ด้วย `__unL33t` + ตัดอักขระก่อนเทียบเสมอ |
| 🛡 กันคำใหม่บังชื่อสมาชิก | คำที่ **เพิ่ม/สลับโหมดรอบนี้** ถูกนำไปเทียบกับ **ชื่อผู้ใช้ของสมาชิกที่มีอยู่** → ถ้าบังคนจริง กล่องสีเหลืองจะบอกว่าบังใคร (ทำเครื่องหมาย **บัญชีแอดมิน** / ถูกระงับ ด้วย) และ **ต้องกดบันทึกซ้ำเพื่อยืนยัน** (ไม่บล็อกถาวร) · บัญชีเดิม **ไม่ถูกเปลี่ยนชื่อ/ไม่ถูกตัดสิทธิ์** · อ่านรายชื่อจากแคชในเครื่อง = **ไม่กินโควตา** (แคชว่างจึงมีปุ่ม “ดึงรายชื่อมาตรวจ” ให้กดเอง) |

- ฟังก์ชัน: `canManageReservedNames()` · `openReservedNamesModal()` · `rvRender()` · `rvAdd()` · `rvRemove(i)` · `rvToggleExact(i,v)` · `rvResetDefaults()` · `rvTest(v)` · `rvSave()` · `refreshReservedBadge()`

### 🚀 หน้าจอโหลด (Loading Screen) — รูปตั้งได้จากแอดมิน (เพิ่ม 14 ก.ย.)

ตอนเปิดแอป / หลังล็อกอิน จะมีจอโหลดที่ **รูปพื้น + ข้อความ + แถบความคืบหน้า + เปอร์เซ็นต์**
ตาหน้าเดียวกันทุกเครื่อง เพราะค่าเก็บที่ **`settings/loading_screen`** (ค่าที่ใช้ร่วมกัน ไม่ใช่ค่าส่วนตัวของใคร)

| ส่วน | รายละเอียด |
|---|---|
| เก็บค่าที่ไหน | Firestore `settings/loading_screen` → `image` (data URL) · `title` · `updatedAt` · `updatedBy` |
| แคชในเครื่อง | `localStorage.taxi_loading_screen_v1` → เปิดแอปครั้งถัดไปเห็นรูปของแอดมิน **ทันที** ไม่ต้องรอเน็ต |
| ใครตั้งได้ | แอดมิน (`Admin`) หรือผู้มีสิทธิ์ `canManageToastMsg` — ทาง **ตั้งค่าการใช้งาน → ⚙️ บริการ/ระบบ → หน้าจอโหลด** |
| อัปโหลดรูป | ย่อให้พอดีกล่อง **≤ 1280×1280 JPEG ≤ 320 KB** ก่อนบันทึก (แนวตั้ง 9:16 → 720×1280 เท่าเดิม · แนวนอน → 1280×720) |
| ตำแหน่งรูป (ซ้าย–ขวา) | **`focusX` (0–100)** — รูปแนวกว้างถูกครอปด้วย `object-fit: cover` จึงเลือกได้ว่าจะโชว์ส่วนไหน (ค่าเริ่มต้น 50 = กลาง) |
| วิธีเลื่อน | **ลากบนรูปพรีวิว** หรือสไลเดอร์ “ตำแหน่งรูป (ซ้าย ↔ ขวา)” + ปุ่ม “กลาง” — ดูผลทันทีในกล่องพรีวิว |
| ดาวน์โหลด / ลบ | มีทั้งคู่ — “ลบรูป” = กลับไปใช้พื้นสำเร็จรูปของแอป |
| ทดลองดู | ปุ่ม “ทดลองดู” โชว์จอโหลดจริง แล้วค้างที่ 100% จนแตะปิด (ดูมุมที่เลือกไว้ของจริงก่อนบันทึก) |

**กติกาที่ห้ามพลาด (รวมบทเรียนจากเคสจริง 14 ก.ย.):**

- **ห้ามปิดจอโหลดด้วย `appLoader.style.display = 'none'` ในเส้นทางปกติ** — ให้เรียก `window.__lds.finish()`
  (วิ่งถึง 100% แล้วจางหาย) หรือ `window.__lds.forceHide()` (ซ่อนทันที/ตอนระบบพัง) ไม่งั้นจะไม่เห็นแถบความคืบหน้า
  · ยกเว้น **NUCLEAR FALLBACK 10 วินาที** ที่ตั้งใจให้ซ่อนทึบเสมอ
- **ทุกการซ่อนมี “รุ่น” (`gen`)** — `restart()` เพิ่มรุ่น ทำให้คิวซ่อนของรอบเก่าถูกยกเลิก
  (บั๊กที่เจอตอนทดสอบ: กด “ทดลองดู” ซ้ำเร็ว ๆ แล้วจอโหลดถูกคิวเก่าซ่อนทิ้งกลางทาง)
- **สคริปต์หน้าจอโหลดอยู่ “ก่อน” ตัวจอโหลดใน DOM** (บรรทัด ~1810 vs ~2080) → การทารูปต้องทำ **3 จุด**:
  ① ตอนอ่านแคช ② เมื่อ `DOMContentLoaded` ③ ที่ท้าย `<body>` ก่อนเรียก `loadLoadingScreenConfig()`
  ไม่งั้นจะเจอเคส **“รีเฟรชแล้วรูปไม่ขึ้น”** (ทาไม่เจอ element แล้วเงียบ ๆ ไป)
- **ใช้ `<img>` ไม่ใช่ CSS `background-image`** — จุดสำคัญคือ **ตรวจสอบได้จริง** ว่าเบราว์เซอร์ถอดรหัสแล้ว
  (`naturalWidth > 0`) และ data URL ขนาด 150–300 KB ใน background-image มีโอกาสถูกมองข้ามแบบเงียบ ๆ
- **ทุกชั้นของจอโหลดต้องมี `z-index` กำกับ** — รูป(1) → พื้นสำเร็จรูป(0) → ม่านเงา(2) → ข้อความ(3)
  ถ้าปล่อยให้เรียงตามลำดับ DOM เฉย ๆ ชั้นพื้นทึบที่อยู่ทีหลังจะ **วาดทับรูป** (อาการ: “รูปติดตั้งแล้วแต่ไม่ขึ้น”)
  · ตัวตรวจในหน้าตั้งค่ามีบรรทัด **“รูปไม่ถูกชั้นอื่นบัง”** ที่เช็ค `elementsFromPoint` จริง ไม่ใช่ดูแค่ค่าในตัวแปร
- **ยิงคำขอค่าหน้าจอโหลดจาก “ต้นไฟล์”** (พร้อม `preconnect` ไป firestore.googleapis.com) — ไม่งั้นค่ามาถึงช้า ~2.5 วิ
  แล้วจอโหลดปิดไปก่อน · เครื่องใหม่ที่ยังไม่มีแคชจะ **รอสูงสุด 2.2 วิ** และให้เห็นรูป ~0.9 วิ ก่อนปิด
  (เครื่องที่มีแคช: รูปขึ้นใน ~0 ms และปิดที่ ~0.7 วิ — ไม่หน่วงเลย)
- **“ทดลองดู” = ค้างที่ 100% จนกว่าจะแตะปิด** (มีข้อความ “แตะตรงไหนก็ได้เพื่อปิด” + ประตูนิรภัย 60 วิ)
  แล้วกลับเข้าหน้าตั้งค่าเดิม — ห้ามเด้งกลับเองแบบเดิม
- เพิ่มขั้นตอนจริงได้ด้วย `window.__lds.step(40, 'กำลังโหลด...')` — แถบวิ่งเองถึง 92% แล้วรอสัญญาณ “พร้อม” จริง
- **`focusX` เป็นค่าที่ใช้ร่วม (`settings/loading_screen`) ไม่ใช่ค่าส่วนตัว** — เขียนด้วย `integerValue` (ตาม `__fsRestPatchDoc`)
  และอ่านได้ทั้งจากแคช/เซิร์ฟเวอร์ · **ถ้าฟิลด์หายไป ต้องคงค่าเดิมไว้ ห้ามรีเซ็ตเป็น 0** (`__ldsApply` ทำเช่นนั้น)
  · ตอน boot ต้องเซ็ต `object-position` **ทุกครั้งที่ทา `src`** ไม่งั้นรูปที่แคชไว้จะกลับไปกลางเอง
- **ตัวตรวจที่ใช้ได้ทันที:** `window.__ldsState()` (รูปมาจากไหน/ถอดรหัสได้ไหม/เขียนแคชได้ไหม/`focusX`) ·
  `window.__ldsTrace` (ลำดับการทา) · `window.__ldsHiddenAt` (เวลาที่จอโหลดปิด) — ไม่ต้องเดาอีก
- ดึงค่าล่าสุดตอนบูตที่ `window.loadLoadingScreenConfig()` (เรียกก่อน `listenAppConfig()`) — เอกสารยังไม่มี = 404 เป็นเรื่องปกติ

### 🔒 ล็อกการเลือกข้อความ + ลากบนรูปแล้วเลื่อนหน้าจอได้ (เพิ่ม 15 ก.ย.)

ทั้งแอปล็อกไม่ให้เลือก/คัดลอกข้อความแล้ว (เหมือนแอปมือถือ) และ **ลากนิ้ว/เมาส์บนรูป**
(เช่น QR Code รับเงิน) **เลื่อนหน้าจอได้ตามปกติ** — ไม่ต้องลากหลบไปนอกกรอบรูปอีก

| กฎ | รายละเอียด |
|---|---|
| ล็อกการเลือก | `body { user-select: none; -webkit-touch-callout: none }` — ครอบทุกหน้าจอ/หน้าต่าง (รวมข้อความในการ์ด) |
| ข้อยกเว้น | **ช่องกรอกทุกชนิด** (input · textarea · select · contenteditable) ยังเลือก/คัดลอก/แก้ได้ · หรือใส่คลาส **`.allow-select`** ที่กล่องไหนก็ได้ถ้าอนาคตอยากให้เลือกได้ |
| ลากบนรูป | `img, picture, video, svg { -webkit-user-drag: none; touch-action: manipulation; -webkit-touch-callout: none }` → เบราว์เซอร์ไม่เริ่มท่าทาง “ลากรูป” อีก |

**กติกาที่ห้ามพลาด:**

- ⛔ **ห้ามใช้ `pointer-events: none` กับรูป** เพื่อแก้ปัญหานี้ — จะทำ “แตะรูปเพื่อเปลี่ยนรูป” (รูปโปรไฟล์/QR/หน้าจอโหลด) พังทันที
- ⛔ **ห้ามครอบ `canvas`** ในกฎนี้ — แผนที่ Mini Map (`#navMini canvas`) ต้องรับท่าลาก/ซูมเอง (ตั้ง `touch-action: none` ไว้)
- การคัดลอกลิงก์ใช้ Clipboard API (`window.copyAppShareLink`) ไม่พึ่งการเลือกข้อความ → ไม่พังโดยกฎนี้
- ตรวจในพรีวิว: `getComputedStyle(document.body).userSelect` = `none` · ของ `input` = `text` ·
  รูป `webkitUserDrag` = `none` และ `elementFromPoint` กลางรูปต้องได้ตัว `<img>` (ไม่ใช่ชั้นอื่นทับ)

### 🖱️ แถบเลื่อนในลิสต์ค้นหา — แอดมินตั้งค่าเอง (เพิ่ม 15 ก.ย.)

ลิสต์ **ที่โปรด / ประวัติล่าสุด / ผลค้นหา** เดิมซ่อนแถบเลื่อนไว้ทุกอุปกรณ์ → จอคอมต้องใช้ล้อเมาส์เท่านั้น
ตอนนี้แอดมินเลือกได้ว่าจอคอมจะเห็นแถบเลื่อนไหม + หนา/จางแค่ไหน โดย **ทุกเครื่องใช้ค่าร่วมกัน**

| ส่วน | รายละเอียด |
|---|---|
| เข้าที่ไหน | **ตั้งค่าการใช้งาน → ⚙️ บริการ/ระบบ → แถบเลื่อนในลิสต์ค้นหา** (แอดมิน หรือผู้มีสิทธิ์ `canManageToastMsg`) |
| ครอบคลุมอะไร | **ลิสต์ ที่โปรด/ประวัติ/ผลค้นหา** · **หน้าต่างทุกบาน** (`.modal-content-scroll` · `.tracker-zoom-box`) · **เมนูแฮมเบอร์เกอร์** (`.side-menu-items`) · **แถบหมวดไอคอน** (`#iconPickerMatTabs` — แนวนอน) |
| ปรับอะไรได้ | **โชว์/ไม่โชว์** · **ความหนา 6–18 px** · **ความจาง (ทึบ) 10–100%** + กล่องตัวอย่าง 8 รายการที่เลื่อนได้จริง |
| เก็บค่าที่ไหน | Firestore `settings/ui_prefs` → `sbOn` · `sbW` · `sbA` · `updatedAt` · `updatedBy` |
| แคชในเครื่อง | `localStorage.taxi_ui_prefs_v1` → ทาค่าตั้งแต่เฟรมแรกของแอป แล้วค่อยดึงของจริงจากเซิร์ฟเวอร์ทับ |
| มีผลกับใคร | **ทุกเครื่องที่มีเมาส์** (`hover:hover` + `pointer:fine`) — มือถือ/จอสัมผัสปัดนิ้วเหมือนเดิม ไม่มีแถบโผล่ |
| ค่าเริ่มต้น | โชว์ · หนา 10 px · ทึบ 50% (ยังไม่มีเอกสารบนเซิร์ฟเวอร์ = ใช้ค่านี้ · ไม่ขึ้นเดือนผิด) |
| ยืนยันก่อนบันทึก | มีด่านยืนยันตัวตน (รหัสผ่าน/PIN) เพราะมีผลกับทุกคน — เหมือนหน้าจอโหลด |

**กติกาที่ห้ามพลาด (กับดักที่เจอจริงตอนทำ):**

- ⚠️ **Chrome จะเลิกใช้ `::-webkit-scrollbar` ทั้งชุด ทันทีที่ `scrollbar-width` ไม่ใช่ `auto`** — บรรทัด
  `.dropdown-box { scrollbar-width: none; }` ที่เขียนไว้แต่แรก (เพื่อซ่อนแถบ) ทำให้ความหนาที่ตั้งไม่มีผลเลย
  → บล็อกใหม่ต้องถอยกลับเป็น `scrollbar-width: auto` **ก่อน** แล้วปิดด้วยคลาส `html.sb-off` ตอนผู้ใช้เลือก “ไม่โชว์”
- **Firefox ไม่รองรับ `::‑webkit‑scrollbar`** → ใช้ `scrollbar-width: thin` + `scrollbar-color` ใน `@supports (-moz-appearance: none)`
- **โหมดสว่างต้องใช้ทองเข้ม** (`#b07c00` = `--neon-yellow` ของธีมสว่าง) ไม่ใช่ทองอ่อน `rgba(255,210,77,…)` เพราะบนพื้นขาวจางเกิน
- ตรวจผลด้วยการวัดจริง: `offsetWidth − clientWidth` (กล่องเลื่อนแนวตั้ง) หรือ `offsetHeight − clientHeight` (แถบแท็บแนวนอน)
  ต้องเท่ากับค่าที่ตั้ง (±1–2 px จากขอบ) — ค่าที่วัดได้ตอนทำ: `w=10 → 10` · `w=18 → 19` · `w=6 → 7` · ปิด → 1 · แถบแท็บแนวนอน 9px
- **ห้ามตั้ง `scrollbar-width` แบบ inline** (เช่นใน `enableDesktopHScroll`) — inline ชนะกฎกลางทุกตัว และทำให้ Chrome ทิ้ง `::-webkit-scrollbar`
- เมนูแฮมเบอร์เกอร์ต้องมี `overflow-y: auto` + **`min-height: 0`** ที่ `.side-menu-items` ไม่งั้นรายการท้าย (ออกจากระบบ) ล้นจอบนเครื่องจอเตี้ย
- **404 ของ `settings/ui_prefs` = “ยังไม่เคยตั้งค่า” ไม่ใช่ข้อผิดพลาด** → ห้ามขึ้น toast เตือน (แยก “เซิร์ฟเวอร์ตอบแล้ว” จาก “ดึงไม่ได้”)

### 📏 ระยะทางในลิสต์ “ที่โปรด / ประวัติล่าสุด” (เพิ่ม 15 ก.ย.)

### 🆕 สมาชิกใหม่ (รายวัน) — แอดมินรู้ว่าใครสมัครเข้ามา (เพิ่ม 14 ก.ย.)

##### 🕓 ประวัติการจัดการในศูนย์แจ้งเตือน (เพิ่ม 14 ก.ย.)

ส่วนท้ายของศูนย์แจ้งเตือนมี **“ประวัติการจัดการ”** ตอบคำถามว่าเรื่องไหนถูกจัดการไปแล้ว **เมื่อไหร่ · ใครกด · กี่นาทีจากตอนเกิดเรื่อง**
เก็บใน **`localStorage.taxi_notif_history_v1`** (เครื่องนี้เท่านั้น — **ไม่เขียนขึ้นเซิร์ฟเวอร์ จึงไม่กินโควตา**) เก็บล่าสุด **40 รายการ**

| เรื่อง | “ตอนเกิดเรื่อง” คำนวณจาก | จดตอนไหน |
|---|---|---|
| สมาชิกใหม่ | `__signupFirstUnseenAt` = เวลาสมัครของคนที่ยังไม่เปิดดู (เก่าสุด) | `markSignupsSeen()` ตอน **เปิดดูรายชื่อ** (ยอดก่อนล้าง) |
| คำขอสิทธิ์เพิ่ม | `requestedAt` ของคำขอที่ยัง `pending` (เก่าสุด) | `approvePermRequest` / `rejectPermRequest` |
| เที่ยวที่ยังไม่ขึ้นเซิร์ฟเวอร์ | `tripQueueOldestQueuedAt()` = เที่ยวในคิวที่เข้าคิวก่อนสุด | `drainTripSyncQueue()` เมื่อ **ส่งสำเร็จ ≥ 1 เที่ยว** |

**กติกาที่ห้ามพลาด:**

- **จดเฉพาะตอนเรื่อง “จบจริง”** — การเปิดดูเมนูเฉย ๆ ไม่ใช่การจัดการ (ไม่งั้นประวัติเต็มไปด้วยขยะ)
- **ไม่มีเรื่องค้าง (count = 0) → ห้ามจด** และ **ไม่รู้เวลาที่เกิดเรื่อง → จดพร้อม `ageMs: null`** แล้วขึ้นว่า “ไม่ทราบเวลาที่เกิดเรื่อง” — **ห้ามเดาเวลาให้ดูสวย**
- กันจดซ้ำด้วย `window.__notifLogGuard[key]` (ไม่จดคีย์เดิมซ้ำภายใน **5 วินาที**) — เพราะกดครั้งเดียวอาจวิ่งผ่าน 2 จุด
- ชื่อคนกดใช้ `notifWhoAmI()` = `myCurrentDisplayName` → `myCurrentUsername` → `fmtUname(uid)` — **ห้ามโชว์รหัส uid**

#### 🧩 จัดกลุ่มเมนูใน “ตั้งค่าการใช้งาน” — ลากข้ามหัวข้อ + สร้างหัวข้อเอง (เพิ่ม 14 ก.ย.)

กดค้างที่เมนูใน **ตั้งค่าการใช้งาน** ~0.56 วิ → เข้าโหมดลาก → **ลากเมนูข้ามหัวข้อได้ทุกหัวข้อ** (ไม่จำกัดอยู่แต่หัวข้อเดิม)
เปิดค้างไว้ทั้งหน้าตั้งค่าเพื่อให้เข้าใจโครงทั้งหมด:

| ส่วน | รายละเอียด |
|---|---|
| เข้าโหมดลาก | กดค้างที่เมนู **0.56 วิ** (เงียบ 0.11 + แถบนับถอยหลัง 0.45) · ออกเมื่อแตะพื้นที่ว่าง / ปุ่มปิด / ปุ่มย้อนกลับ |
| ลากข้ามหัวข้อ | ปล่อยลงในหัวข้อที่นิ้วอยู่ → เมนูย้ายไปหัวข้อนั้นทันที (จำตาม **เวลาที่นิ้ว** ไม่ใช่กึ่งกลางการ์ด) |
| ➕ สร้างหัวข้อใหม่ | ปุ่มในแถบคำแนะนำ → ตั้งชื่อ (+ ใส่ emoji ได้) → ลากเมนูไปวาง |
| ✏️ เปลี่ยนชื่อหัวข้อ | ปุ่มดินสอท้ายหัวข้อ — ใช้ได้ทั้งหัวข้อตั้งต้นและหัวข้อที่สร้างเอง |
| ✏️ แก้ข้อความเมนูรายตัว | **ปุ่มดินสอท้ายชื่อเมนู** (ในโหมดลาก · แอดมินเท่านั้น) — ใช้ได้ทั้ง **เมนูแฮมเบอร์เกอร์** และ **ตั้งค่าการใช้งาน** · กดแล้วแก้ชื่อ/คำอธิบายของเมนูนั้นได้ทันที ทางหน้าต่างเล็ก (ไม่ต้องเปิดลิสต์ยาว) |
| 🗑 ลบหัวข้อ | ปุ่มถังขยะ (เฉพาะหัวข้อที่สร้างเอง) — เมนูที่อยู่ในหัวข้อนั้นย้ายกลับหัวข้อแรกให้เอง |
| หัวข้อที่ไม่มีเมนู | **ซ่อนหัวข้อเองอัตโนมัติ** · ตอนโหมดลากจะกลับมาแสดงพร้อมช่องจุดเส้น “วางเมนูที่นี่” เพื่อให้ลากกลับเข้าได้ |

**กติกาที่ห้ามพลาด (กับดักที่เจอจริงตอนทำ):**

- หน้าตั้งค่าการใช้งาน **ห้ามกลับไปใช้ `applySavedMenuOrder()`** — ฟังก์ชันนั้นบังคับให้เมนูกลับเข้ากลุ่มเดิมทุกครั้ง ⇒ ลากข้ามหัวข้อจะไม่ติด ให้ใช้ `window.applyHubLayout()` เท่านั้น
- **ตอนลากต้องใช้ตำแหน่งนิ้ว (`drag.lastY`) ตัดสินหัวข้อ** ไม่ใช่ `getBoundingClientRect()` ของการ์ดที่ลาก — การ์ดมีการชดเชย `staticShift` ทำให้หัวข้อไม่เปลี่ยนตามนิ้ว
- **บันทึก “เมนู↔หัวข้อ” ก่อนซิงก์ Firestore** (`hubSaveCatsFromDom()` ต้องมาก่อน `saveMenuOrderToDB()`) ไม่งั้นเครื่องอื่นจะได้แผนผังหัวข้อเก่า
- รับค่าส่วนกลาง (`settings/menuOrder`) **เฉพาะเมื่อมีของจริง** — `hubItemCat` เป็น `{}` ทั่วไป อย่าเอามาทับของในเครื่อง

**⏳ กดค้างเข้าโหมดลากให้ “ติดง่าย” บนมือสั่น/รถสั่น โดยไม่แลกกับการเลื่อนเมนู (เพิ่ม 15 ก.ย.):**

เดิมต้องกดค้าง **0.9 วิ** และ **450 มิลลิวแรกไม่มีสัญญาณอะไรเลย** — ผู้ใช้จึงปล่อยมือก่อนครบเวลาแล้วคิดว่าไม่ติด
ตอนนี้ใช้ 3 กลไกที่ **ไม่แตะ `touch-action` เลย** (จึงไม่กระทบการเลื่อนเมนูแม้แต่นิดเดียว):

| กลไก | ค่า | ทำไมเลือกทางนี้ |
|---|---|---|
| ย่นเวลากดค้าง | 900 → **560 มิลลิว** (110 เงียบ + 450 นับถอยหลัง) | ช่วงที่นิ้ว/รถต้อง “นิ่งพอ” สั้นลงเกือบครึ่ง แต่ยังยาวกว่า **แตะ** (ปกติ <200 มิลลิว) พอที่จะไม่เข้าโหมดโดยบังเอิญ |
| สัญญาณให้เห็น + สัมผัส | ขอบทอง + **แถบวิ่ง** (`--arm-ms`) + `navigator.vibrate(8)` ตอนเริ่มนับ · `vibrate(30)` ตอนเข้าโหมด | ผู้ใช้รู้ว่าต้องกดต่ออีกนิด และรู้ว่า “ติดแล้ว” โดยไม่ต้องละสายตาจากถนน |
| เผื่อการขยับ | **18px** (เดิม 10px) | ช่วยเมาส์และจุดที่ไม่มีอะไรให้เลื่อน — **ไม่ได้ทำให้เลื่อนจอเสีย** เพราะบนจอสัมผัส เบราว์เซอร์ยิง `pointercancel` เองทันทีที่เริ่มลากจอจริง |

- **กับดักที่ห้ามพลาด:** ห้ามแก้ปัญหานี้ด้วย `touch-action: none` ที่ตัวเมนู (จะ “ล็อก” การเลื่อนเมนูทั้งอัน) และห้ามใส่ `touch-action` ตอนกดค้างไปแล้ว — เบราว์เซอร์อ่านค่านี้ **ณ วินาทีที่เริ่มแตะ** เท่านั้น
- **ทางเลือกที่เผื่อไว้** (ถ้ายังติดยากบนเครื่องจริง): ย้ายจุดกดค้างไปที่ **แถบหัวเมนู/ปุ่มที่ไม่มีพื้นที่เลื่อน** แล้วให้เฉพาะจุดนั้นเป็น `touch-action: none` — คนละสัญญาปัญหากับการเลื่อนเมนู
- วัดผลแล้วในหน้าจริง: สัญญาณขึ้นที่ **111 มิลลิว** · เข้าโหมดที่ **562 มิลลิว** · ขยับ 25px = ยกเลิก · ขยับ 14px = ยังติด · แตะ 90 มิลลิว = ไม่ขึ้นสัญญาณและไม่เข้าโหมด · `pointercancel` = ยกเลิก + เก็บกวาดครบ
- ที่เก็บในเครื่อง: `hub_cats_v1` (รายชื่อหัวข้อ) · `hub_item_cat_v1` (เมนู↔หัวข้อ) · `menu_order_hub` (ลำดับ) — อ่านจากเครื่องก่อนเสมอ (ไม่ต้องรอเน็ต)
- **ซิงก์ขึ้นเซิร์ฟเวอร์พร้อมลำดับเมนู:** `settings/menuOrder` เก็บ `hubCats` + `hubItemCat` เพิ่มจาก `side`/`hub` เดิม ⇒ แอดมินจัดไว้แล้ว **เครื่องอื่นเห็นเหมือนกัน** · ซิงก์ผ่านตัวฟัง `listenGlobalMenuOrder` ที่มีอยู่แล้ว จึง**ไม่มีการอ่านเอกสารเพิ่ม** (เขียนเพิ่มเท่านั้นตอนบันทึก)

#### 🔑 PIN ยืนยันรายการสำคัญ — ตั้งเองได้ทุกบัญชี (เพิ่ม 14 ก.ย.)

ด่านยืนยันตัวตนเดิมบังคับให้พิมพ์ **รหัสผ่านเต็ม** ทุกครั้งที่แก้ข้อมูลสำคัญ (11 จุด) ซึ่งช้าเกินไปตอนอยู่หน้ารถ
ตอนนี้แต่ละบัญชี **ตั้ง PIN 6 หลักของตัวเอง** แล้วใช้ PIN ยืนยันแทนได้ · PIN ของบัญชีอื่นไม่เกี่ยวข้องกันเลย
บนมือถือ **แป้นตัวเลขเด้งขึ้นเอง** (ไม่มีคีย์บอร์ดระบบบังจอ) และลงทะเบียน **“ปลดล็อกด้วยเครื่อง”** ไว้ใช้ Face ID / ลายนิ้วมือ / PIN เครื่องแทนได้อีกทาง

| ส่วน | รายละเอียด |
|---|---|
| ตั้ง/เปลี่ยน/ลบ PIN | ตั้งค่าโปรไฟล์ → การ์ด **“PIN ยืนยันรายการสำคัญ”** (ทุกบทบาท ตั้งได้เอง รวมแอดมิน) |
| ต้องยืนยันรหัสผ่านบัญชีก่อนตั้ง | กันคนอื่นที่หยิบเครื่องที่ล็อกอินค้างไว้มาตั้ง PIN แทนเจ้าของ |
| ใช้ PIN ตอนไหน | กล่อง “ยืนยันตัวตนอีกครั้ง” จะ **ถาม PIN ก่อนอัตโนมัติ** ถ้าบัญชีนั้นมี PIN · มีลิงก์ “ใช้รหัสผ่านแทน” และ “ลืม PIN?” |
| ⌨️ แป้นตัวเลขเด้งเอง | แตะช่อง PIN → แป้นเด้งจากด้านล่าง (จุด 6 จุดติดตามที่กด) · **ไม่มีคีย์บอร์ดระบบบังจอ** · คีย์บอร์ดจริงก็พิมพ์ได้ · สั่นแผ่วทุกครั้งที่กด · ครบ 6 หลัก = ยืนยันเอง |
| ⚪ หน้าตาปุ่มบนแป้น | ปุ่ม**วงกลม** 76px กดง่ายด้วยนิ้วโป้ง · **กดแล้วติดสีชัด**: ปุ่มเลข → พื้นเขียว/ตัวเลขเข้ม · ปุ่มลบ (⌫) → พื้นแดง/ไอคอนขาว · มีวงแหวนเรืองแสงรอบปุ่มที่กด + ย่อลงเล็กน้อย (รวมตอนใช้คีย์บอร์ดจริงพิมพ์) |
| 🔓 ปลดล็อกด้วยเครื่อง | ลงทะเบียนไว้แล้วแตะที่กล่องยืนยัน → **เด้งหน้าปลดล็อกของโทรศัพท์เอง** (Face ID / ลายนิ้วมือ / PIN เครื่อง) · ตัวเลขเครื่องไม่เข้าแอปเลย · ลงทะเบียนต่อเครื่อง (credential ผูกกับอุปกรณ์) |
| ลืม PIN | กด “ลืม PIN?” → ยืนยันรหัสผ่านบัญชี → ตั้ง PIN ใหม่ (ไม่ต้องรอแอดมิน) |
| กันเดา | ผิด 5 ครั้ง → **ล็อก 5 นาที** (ผูกกับบัญชีนั้นในเครื่องนั้น) · แม้ใส่ PIN ถูกก็ไม่ผ่านระหว่างล็อก |
| รูปแบบที่ปฏิเสธ | ไม่ใช่ตัวเลข · ไม่ครบ/เกิน 6 หลัก · เลขซ้ำตัวเดียว (000000) · เลขเรียงติด (123456/654321) · ชุดเดาง่าย (123123/696969) · เลขอ่านกลับหลังได้เหมือนเดิม |

**ทำไม PIN ของ admin กับ user เป็น 123456 เหมือนกันแล้วไม่ชนกัน**

PIN **ไม่ใช่ตัวชี้ตัวตน** — แอปรู้อยู่แล้วว่ากำลังใช้บัญชีไหน (`loggedInUserId` จากตอนล็อกอิน)
จึงเก็บ `users/{uid}.pinHash` แล้วเทียบกับเอกสารของบัญชีนั้นเท่านั้น ⇒ ตัวเลขเดียวกันแต่ **salt คนละตัว → hash คนละค่า**
(แฮชด้วย `pwHash()` = PBKDF2-SHA256 100,000 รอบ + salt ต่อบัญชี · **ไม่เก็บตัวเลขจริงที่ไหนเลย**)

**กติกาที่ห้ามพลาด:**

- **ห้ามใช้ PIN เป็นตัวชี้ตัวตน** — ห้ามค้นหาผู้ใช้ด้วย `pinHash` หรือทำ index เทียบ PIN ข้ามบัญชี (กินโควตาอ่านมหาศาลและรั่วข้อมูล)
- **ห้ามเก็บ PIN ตัวเลขจริงในเครื่อง** — แคชได้เฉพาะ `taxi_pin_cache_v1 = { uid: pinHash }` เพื่อให้ออฟไลน์ยืนยันได้
- **ตั้ง/เปลี่ยน PIN ต้องยืนยันรหัสผ่านบัญชีก่อนเสมอ** — PIN เป็น “ทางลัดยืนยัน” ไม่ใช่ทางตั้ง
- **ต้องรักษา id เดิม** ของกล่อง `sysReauth` (`raPassword` · `raError` · `raDesc` · `raBtnOk` · `raBtnCancel`) — โค้ดที่เรียก `requireReauth()` 14 จุดพึ่งพามัน
- ล็อกเก็บที่ `taxi_pin_lock_v1` — เป็นรายเครื่อง **ไม่ซิงก์ขึ้นเซิร์ฟเวอร์** (เครื่องอื่นไม่ถูกหน่วงไปด้วย)
- **อ่าน PIN ของเครื่องไม่ได้ — และไม่ต้องพยายาม** เบราว์เซอร์ไม่มี API ให้อ่านรหัส/ลายนิ้วมือของโทรศัพท์ · สิ่งที่ทำได้คือให้ **หน้าปลดล็อกของเครื่องเป็นคนตรวจ** (WebAuthn) แล้วรับมาแค่ผลผ่าน/ไม่ผ่าน
- **WebAuthn รับเฉพาะ “ชื่อโดเมน” ไม่รับ IP** ⇒ ใช้ได้บน `https://baby4bot.github.io/taxi/` · ที่อยู่แบบ `127.0.0.1` จะขึ้นเตือนว่าใช้ไม่ได้ (ไม่ใช่บั๊ก)
- **แป้นตัวเลขต้องมี z-index สูงกว่ากล่องยืนยันตัวตน** (`#sysReauth` = `100050` ⇒ แป้นใช้ `300000`) ไม่งั้นแป้นจะอยู่หลังกล่อง กดไม่ได้
- **อย่าลบคลาส `.pad-key` / `.pad-del`** — กฎปุ่มวงกลมและสีตอนกดผูกกับคลาสนี้ · `pinPadPress()` เติมคลาส `pressed` เอง 130ms เพื่อให้ปุ่มติดสีตอนกดด้วยคีย์บอร์ดจริงด้วย
- `devUnlockPrompt()` เป็นการยืนยัน **ฝั่งเครื่องเท่านั้น** (ไม่มีเซิร์ฟเวอร์ตรวจลายเซ็น) — เพิ่มความยากให้คนที่หยิบเครื่อง แต่ไม่ใช่หลักฐานทางกฎหมาย

| ⚙️ ค่าที่สมาชิกตั้งเองได้ | ธีม · ประเภทรถ · เบิกเวลาจอด · โหมดทางด่วน · สั่น · เสียงติ๊ง · เริ่มต่ออัตโนมัติ · เต็มจออัตโนมัติ | อ่านจากเอกสารที่โหลดมาแล้ว |
| 🔢 ตั้ง PIN ใหม่ให้สมาชิก | ช่อง PIN 6 หลัก 2 ช่อง + ปุ่มฟ้า (โชว์เฉพาะคนมีสิทธิ์แก้สมาชิก) | ตรวจรูปแบบ (6 หลัก · ไม่ซ้ำ · ไม่เรียง) → **ยืนยันตัวตนก่อน** → แฮช PBKDF2 ใหม่ทุกครั้ง → เขียนทับ `pinHash` |
| 🔄 รีเซ็ต PIN ของสมาชิก | ปุ่มแดง (โชว์เมื่อมี PIN) | **ต้องยืนยันตัวตนของผู้ทำรายการก่อน** แล้วเขียน `pinHash: ''` + บันทึก log |

**กติกาที่ห้ามพลาด:**

- **ห้ามแสดงแฮชเต็มในหน้าจอ** — รายงานได้แค่ “มี/ไม่มี” และ “ตั้งเมื่อไหร่ · ใครตั้ง” พอ (แฮชเต็มเปิดช่องให้ไล่เดารหัสนอกระบบ)
- **อ่านจาก `currentAdminUsers` เท่านั้น** — ห้ามยิง `getDoc` เพิ่มต่อการเปิดหน้าจัดการผู้ใช้ 1 ครั้ง (กินโควตาโดยไม่จำเป็น)
- **รีเซ็ต PIN ต้องยืนยันตัวตนก่อนเสมอ** (`requireReauth`) — ไม่งั้นคนที่หยิบเครื่องแอดมินที่ล็อกอินค้างไว้จะล็อกสมาชิกออกจากระบบได้
- **หลังรีเซ็ต PIN ต้องล้างแคชในเครื่องสมาชิกด้วย** — `listenToMyUser` ซิงก์ `pinCacheSet(uid, data.pinHash)` เมื่อ `pinHash` ว่าง ⇒ ถ้าไม่ล้าง **PIN เก่ายังใช้ยืนยันได้** (กับดักนี้ปิดแล้วในโค้ด · ห้ามถอดออก)
- **แอดมินตั้ง PIN ให้สมาชิกได้ แต่ห้ามเห็น PIN ของสมาชิก** — ช่องที่เพิ่มเป็น **ทางเดียว** (พิมพ์ใหม่เท่านั้น) เพราะระบบเก็บแฮช ไม่มีตัวเลขจริงให้ดึงมาโชว์ · `pinSetBy` เก็บว่าใครเป็นคนตั้ง
- **ตั้ง PIN ให้ตัวเองต้องอัปเดตแคชในเครื่องด้วย** — ถ้าลืม `pinCacheSet(uid, hash)` ตอน `uid === loggedInUserId` **PIN ใหม่จะยังใช้ยืนยันไม่ได้** จนกว่าจะปิด-เปิดแอป

**กติกาที่ห้ามพลาด:**

- **คีย์ของ override คือ “ข้อความต้นฉบับ”** ⇒ ข้อความที่เหมือนกันจะเปลี่ยนพร้อมกันทุกจุด (เช่นคำว่า “บันทึก” 3 จุด) — ต้องตรวจจำนวน “N จุด” ที่แสดงในแต่ละแถวก่อนบันทึก
- **รหัส/คีย์ของ Map ที่จำต้นฉบับคือ text node** (`window.__txtNodes`) และ `applyTextOverrides()` เซ็ตค่าจาก **ต้นฉบับเสมอ** ⇒ ห้ามเปลี่ยนไปต่อข้อความจาก DOM ตรง ๆ ไม่งั้นลบ override แล้วข้อความจะค้าง
- **ห้ามแก้ text node** ของ `#pinPadGrid` / `.pad-key` / `.material-symbols-outlined` / `[data-txt-skip]` — เลขบนคีย์แพด PIN ต้องคงอยู่ (มีด่านใน `textOvrSkip()`)
- **ตัวเลข/เปอร์เซ็นต์ล้วนถูกข้าม** (เช่น `41%` · `15:30` · `1,481`) กันข้อความที่ระบบอัปเดตเองถูกเขียนทับ
- **บันทึก/รีเซ็ตต้องยืนยันตัวตนก่อนเสมอ** (`requireReauth`) และ **เฉพาะ Admin** เท่านั้น
- **ห้ามเช็คสิทธิ์ด้วย `window.currentUserRole`** — ตัวจริงคือ `currentUserRole` ในสคริปต์ (มีตัวช่วย `window.isAdminNow()` / `window.myRoleNow()` ให้ใช้)เคยเจอบักจริง: เมนูและปุ่มของแอดมิน **ไม่โผล่ในเครื่องผู้ใช้** เพราะเช็คตัวที่ไม่มีใครตั้งค่า (undefined ตลอด) — ทดสอบในพรีวิวแล้วเห็นขึ้น เพราะตอนเทสต์มีการตั้งค่านั้นมือ ⇒ ต้องทดสอบแบบ **ไม่ตั้งค่าอะไรเลย**
- **ปุ่มรูปตา = เปิดหน้าจอจริง ไม่ใช่แค่ลอกข้อความ** — ถ้าข้อความอยู่ในหน้าต่าง ให้ยืน z-index หน้าต่างนั้นเป็น `10080` **ค้างไว้จนกว่าจะเลิกดู** (`#textEditModal` = `10045` ⇒ ไม่ยกขึ้น = มองไม่เห็น) แล้วคืนค่าเดิมตอน `textPreviewUnmark()` · ถ้าอยู่หน้าหลัก/เมนูข้าง ให้ **ปิดหน้าต่างที่บังอยู่ + หน้าแก้ข้อความก่อน** แล้วโชว์ปุ่มลอย `#txtPrevBackChip` (หายเองใน 20 วิ)
- **ไฮไลต์ = `outline` + `box-shadow` เท่านั้น ห้ามใส่ `background` ทับ** — หัวเรื่องใช้ `background-clip:text` (ตัวอักษรโปร่งใส) ใส่พื้นทับ = ตัวอักษรหายทั้งบรรทัด (เจอจริงกับ “คำนวณค่าแท็กซี่”)
- **ไฮไลต์ต้องค้าง ไม่ใช่กะพริบแล้วหาย** — `.txt-prev-mark` + ตัวเฝ้า (`setInterval` 400ms) ถอดให้เมื่อหน้าต่างนั้นปิด/ข้อความถูกซ่อน · **ห้ามมีป๊อปอัปแจ้งเตือนตอนสำเร็จ** (ผู้ใช้ขอ) — toast แสดงเฉพาะกรณีที่ข้อความยังถูกซ่อนอยู่จริง ๆ เท่านั้น
- **กดตาซ้ำ = ดูจุดถัดไป** (`window.__txtPrevIdx` ต่อข้อความ) — ข้อความเดียวกันอยู่ได้หลายที่
- **ข้อความเดียวกันอยู่หลายที่** — `window.__txtEls` เก็บ **ทุก element** ต่อข้อความ แล้ว `textPreviewRank()` เลือกที่เหมาะสุด (เห็นอยู่แล้ว 100 → หน้าหลัก 40 → เมนูข้าง 30 → หน้าต่างที่เปิดได้ 20 → ซ่อนอยู่ 5) — **ห้ามใช้ element แรกที่เจอ** (เคสจริง: “📍 สรุปเส้นทาง” เจอที่ซ่อนอยู่ก่อน)
- **กรองตามหน้าจอ = ชื่อหน้าจอดึงจาก h3 ของหน้าต่างนั้น** (`textOvrScreenLabel`) จึงตรงกับที่คนขับเห็นและไม่ต้องดูแลแมปเอง — ถ้าไม่มี h3 จึงค่อยตกไปใช้แมปสำรอง
- มี **MutationObserver** ทางาน childList (debounce 180ms) จึงครอบข้อความในหน้าต่างที่เรนเดอร์ใหม่ — งานเขียนข้อความเองไม่ถูกเฝ้า ⇒ ไม่วนลูป

- นับเฉพาะคิวของบัญชีที่ล็อกอินอยู่ (`tripQueueMine()`) — ห้ามเขียนทับคิวของบัญชีอื่นบนเครื่องที่ใช้ร่วมกัน
- คิวว่าง/ส่งสำเร็จ → ป้ายต้องหายทันที (มาจาก `renderTripSyncChip()` → `renderTripSyncAlert()`)

  ห้ามเทียบยอดรวมกับมิเตอร์เด็ดขาด ไม่งั้นทุกเที่ยวที่ขึ้นทางด่วนจะรายงาน “คลาดเคลื่อน” เป็นสิบเปอร์เซ็นต์ทั้งที่ของจริงตรงกัน
- ฟีเจอร์นี้ **วัดอย่างเดียว** — ห้ามแก้สูตรหรือปรับตัวเลขค่าโดยสารให้เองจากผลเทียบ
- เขียนลง Firestore แบบ **merge เฉพาะฟิลด์ `calib`** — ห้ามทับฟิลด์อื่นของเที่ยวที่บันทึกไว้แล้ว
- เขียนไม่สำเร็จ = เข้าคิวเที่ยวเดิม (`taxi_pending_trips_v1`) แล้วลองใหม่เองเมื่อเน็ตกลับมา
- เที่ยวยังรอซิงก์อยู่ = แปะ `calib` ไว้ในคิวนั้นเลย (ไม่ยิงเซิร์ฟเวอร์ซ้ำ)

### ✖️ ปุ่มกากบาทปิดหน้าต่าง — อยู่มุมขวาบนเสมอ (แก้ 15 ก.ย.)

`.btn-close-floating` ทุกหน้าต่างในแอปตรึงอยู่ **มุมขวาบนของกล่องหน้าต่าง**: `top: 14px; right: 14px; transform: none`
(เดิม `top: 50%` → ปุ่มลอยกลางหน้าต่างและไปทับรายการข้างใน · หน้าต่างยิ่งสูง ปุ่มยิ่งเลื่อนลงมากลางจอ)

- หน้าต่างขยายสูงเท่าไร ปุ่มก็อยู่มุมเดิมเสมอ (ระยะห่างจากขอบบน/ขวาคงที่ไม่เปลี่ยน)
- ปุ่มลัดในหัวหน้าต่าง (`.btn-action-floating` — กุญแจ/รีเฟรช) ขยับขึ้นแถวเดียวกันที่ `top: 14px; right: 62px` — **แก้คู่กันเสมอ**
- ปิดหน้าต่างได้ 3 ทางเหมือนเดิม: กากบาท · แตะพื้นที่ว่างนอกหน้าต่าง · (บางหน้าต่าง) ปุ่มในเนื้อหา

### 📜 ความลื่นบนมือถือ — กฎที่ห้ามพลาด (แก้ 14 ก.ย. · ต่อเติม 15 ก.ย.)

อาการที่ผู้ใช้เจอ: ในลิสต์ **ที่โปรด / ประวัติล่าสุด / ผลค้นหา** ลากขึ้นลงแล้ว “ติด” ไม่ลื่น
ต้องปล่อยนิ้วรอสักพักแล้วลองใหม่ — ต้นเหตุมี 3 อย่าง และทุกอย่างอยู่ในโค้ดนี้ด้วยกัน:

| ❌ ห้ามทำ | ✅ ทำแบบนี้ |
|---|---|
| `backdrop-filter` บน **กล่องที่กำลังเลื่อน** (`.dropdown-box`) | **ตัด blur ออกทุกความกว้าง** (เดิมตัดแค่ ≤900px → จอคอมยังเบลอ = สาเหตุอันดับ 1 ที่ล้อ/แถบเลื่อนสะดุด) → ใช้พื้นทึบ `rgba(16,21,32,0.985)` |
| `position: sticky` + `backdrop-filter` **ในลิสต์ที่เลื่อน** (`.history-header`) | ตัด blur ออกทุกความกว้าง แล้วให้พื้นทึบ (สีกลางวัน/กลางคืนมีแยก) · sticky ได้ แต่ห้าม blur |
| `touchmove` ระดับ `window` แบบ `passive:false` + `capture` → เบราว์เซอร์ต้องรอ JS ทุกเฟรม | ติดตั้งเฉพาะเมื่อ `CSS.supports('overscroll-behavior','contain')` เป็น false (iOS เก่า) และ **ข้ามท่านั้นทั้งท่า** ถ้านิ้วเริ่มในลิสต์ที่เลื่อนได้ |

**รายละเอียดตัวดัก PTR (`lockPullToRefresh`) — หลักการคือ “ข้ามออกเร็วที่สุด”:**

- `SAFE_ZONES` = `.dropdown-box, .modal-overlay, .modal-box, .modal-content-scroll, .side-menu, …`
  ถ้า `e.target.closest(SAFE_ZONES)` → `skipGesture = true` → `onTouchMove` `return` ทันที (ไม่ `preventDefault`) ✔
- **`touchstart` ต้องเบาที่สุด**: จำแค่ `targetEl` + `startY` เท่านั้น — งานหนัก (`closest()` / เดิน DOM / `getComputedStyle`) ย้ายไป `resolveGesture()` ที่คิด **ครั้งแรกที่ต้องใช้จริง**
  ⇒ นิ้วแตะใหม่ทุกครั้งไม่มีงานบน main thread ก่อนเริ่มเลื่อน (ต้นเหตุอาการ “ปัดแล้วต้องรอสักพักกว่าจะเลื่อนต่อ”) — เดิมคิดตอน `touchstart` ทุกครั้ง
- หา “กล่องที่เลื่อนขึ้นได้” **ครั้งเดียวต่อท่า** (เก็บใน `scrollable`) — ห้ามเดิน DOM/`getComputedStyle` ทุกเฟรม (เดิมทำทุก `touchmove` = ต้นเหตุความหน่วง)
- ขั้นตอน `shouldBlockPull(clientY)`: ลากขึ้น/นิ่ง → `false` · ลิสต์ยังเลื่อนขึ้นได้ (`scrollTop > 1`) → `false` · อยู่หัวสุดหน้าแล้วลากลง → `true`
- PTR หลักจริง ๆ คือ CSS `html, body { overscroll-behavior: none }` — ตัว JS เป็นเพียงตัวหนุนของ iOS < 16

**🔒 ล็อกหน้าเว็บด้านหลัง ขณะลิสต์เปิดอยู่ (เพิ่มต่อจากรอบเดียวกัน):**

เดิมลิสต์เปิดอยู่แต่หน้าเว็บด้านหลังก็ยังเลื่อนได้ = **มี 2 ตัวแย่งการเลื่อนกัน** — อีกสาเหตุที่ทำให้นิ้วลากแล้วรู้สึกติด

- ล็อกเฉพาะ **document ตัวนอกสุด** เท่านั้น — ตัวลิสต์เองยังเลื่อนได้ปกติ
- CSS: `html.locked-scroll, html.locked-scroll body { overflow: hidden !important }`
- **iOS เก่าต้องใช้ `position: fixed` ด้วย** (คลาส `lock-fixed`) ไม่งั้นล็อกแล้วหน้าเด้งขึ้นบนสุด → คำนวณ `--locked-scroll-top: -ระยะที่เลื่อนไป`
  **แต่เบราว์เซอร์ที่รองรับ `overscroll-behavior` (Chrome/Android/Safari 16+) ห้ามตรึง body** — การตรึง body ตอนพิมพ์ค้นหา
  ทำให้แป้นพิมพ์/visual viewport ต้องจัดจอใหม่ ⇒ ปัดลิสต์แล้วรู้สึกเหมือนลิสต์ไถลต่อเองหลังหยุดนิ้ว (เช็ค: `html.classList.contains('lock-fixed')` ต้อง false)
- 📱 `<meta name="viewport">` ต้องมี `interactive-widget=resizes-content` — ให้แป้นพิมพ์ Android **ย่อหน้าจอจริง**
  แทนการแพน visual viewport (ค่า default `resizes-visual` = ต้นเหตุเดียวกับข้อบน) **ห้ามถอดออก**
  แล้วคืนต่ำแหน่งด้วย `window.scrollTo(0, lockY)` ตอนปลดล็อก
- ปลดล็อกอัตโนมัติเมื่อปิดลิสต์/เลือกสถานที่ — เฝ้าด้วย **`MutationObserver` ที่ `style` ของ `#historyList`/`#suggestionList`**
  (โค้ดเดิมเซ็ต `style.display` ตรง ๆ หลายจุด → จุดเดียวจบ)
- มี **watchdog 0.8 วินาที** สร้างเฉพาะตอนล็อก → กันล็อกค้างถ้ามีเส้นทางอื่นที่ปิดลิสต์
  + ปลดล็อกเมื่อกลับมาจากพื้นหลัง (`visibilitychange`)
- ตรวจว่าไม่ค้าง: `window.__pageScrollLocked` · `html.locked-scroll` · `getComputedStyle(document.body).overflowY`

**เพิ่มเติมที่กล่องรายการ:** `-webkit-overflow-scrolling: touch` (โมเมนตัมแบบ iOS เก่า) · `overscroll-behavior: contain` (ลากจนสุดลิสต์แล้วไม่ลากหน้าเว็บต่อ)
· `scroll-behavior: auto` · `scrollbar-gutter: stable` (มี/ไม่มีแถบเลื่อน → ข้อความไม่กระโดด) · `contain: layout style`

#### 📜 เลื่อนเนียนขึ้นอีกขั้น — ตัดสาเหตุสะดุดที่เหลือ (แก้ 15 ก.ย.)

รอบนี้เจอว่าเหลือ **6 ต้นเหตุ** ที่ทำให้ “เลื่อนแล้วก็หยุด” (ทั้งคอมและมือถือ) — ดูตารางเต็มใน
[`.freebuff/run.md`](.freebuff/run.md) หัวข้อ “ลิสต์ค้นหา (ที่โปรด/ประวัติ) — กฎความลื่นของการเลื่อน”

| # | ต้นเหตุ | แก้เป็น |
|---|---|---|
| 1 | blur บนกล่องที่เลื่อน (จอคอมกว้างยังเบลออยู่) | ลบ blur ที่ต้นทาง + พื้นทึบ — **ห้ามใส่กลับ** |
| 2 | sticky header ที่ยัง blur | ตัด blur ทุกความกว้าง |
| 3 | `.list-item { transition: 0.2s }` (= `all` → repaint ทั้งแถวทุก hover) | `transition: background-color 0.15s ease` |
| 4 | ไม่มี `touch-action` | `touch-action: pan-y` (ปล่อยท่าลากแนวตั้งให้เบราว์เซอร์จัดการเอง) |
| 5 | **กดค้างช้า ๆ ระหว่างปัด = เริ่มเลือกข้อความ → ลากต่อไม่ได้** (อาการ “ปัดแล้วหยุด” บนมือถือ) | `user-select: none` + `-webkit-touch-callout: none` |
| 6 | ซ่อนแถบเลื่อนทุกอุปกรณ์ → **บนคอมลากแถบเลื่อนไม่ได้เลย** | `@media (hover:hover) and (pointer:fine)` → แถบทองบาง 10px (มือถือยังซ่อนเหมือนเดิม) |

> 🔎 วัดผลในพรีวิว: `getComputedStyle(#historyList)` → `backdropFilter` = `none` · `touchAction` = `pan-y` ·
> `userSelect` = `none` · `offsetWidth - clientWidth > 0` = มีแถบเลื่อนบนคอม
> (พรีวิวบนเครื่องแรงวัดได้ 60fps ไม่มี long task — จึงต้องยึด “ตัดงานที่รู้ว่าแพง” แทนการวัดอาการ)

> ⚠️ ตรวจด้วยตา: เปิดหน้านี้ในมือถือ → แตะช่องค้นหา → ลากในลิสต์ต้องลื่นต่อเนื่อง

## ⏱️ ความน่าเชื่อถือตอนขับจริง (จุดที่ออกแบบมาพิเศษ)

แอปนี้ต้องทนกับสถานการณ์จริงหน้ารถ จึงมีกลไกเฉพาะเหล่านี้:

- 🔁 **เริ่มต่อเที่ยวค้างอัตโนมัติ** — เผลอปิดแอป/รีเฟรช/ย่อหน้าต่างไว้ เปิดใหม่แล้วมิเตอร์เดินต่อให้
  พร้อมเปิดจอมิเตอร์ใหญ่และ **เสียง + สั่นเตือน** ว่ามิเตอร์เริ่มต่อแล้ว (ตั้งค่าเปิด/ปิดได้)
- 🧊 **ตรวจจับ "จอดับ/ล็อกจอ" ด้วยตัวเอง** (เพิ่ม 15 ก.ย.) — ไม่พึ่ง `visibilitychange` อย่างเดียว เพราะบางเครื่อง
  ล็อกจอแล้ว **ไม่ยิง event** → ตัวจับเวลามิเตอร์ (1 วิ) จะถูกเรียกห่างกันผิดปกติ ⇒ ใช้ "การหน่วงของตัวจับเวลา"
  เป็นสัญญาณว่าหน้าไม่ได้อยู่หน้าจอจริง แล้วจดเป็นช่วงซ่อน (หยุดนับเวลารถติดที่ ⚠️ **เดา** เอง + ให้ catch-up ทำงาน)
- 📡 **ปลุก GPS อัตโนมัติ** (เพิ่ม 15 ก.ย.) — Android มักพัก `watchPosition` ตอนล็อกจอ/สลับแอปนาน ⇒ ถ้าไม่มี fix
  เกิน **60 วิ** ระบบจะ `clearWatch` แล้วสร้าง watch ใหม่ให้เอง (และปลุกทันทีตอนกลับมาที่จอ)
  ถ้าไม่มีกลไกนี้ ระยะทางจะหยุดนับเงียบ ๆ ทั้งที่มิเตอร์ยังวิ่ง (เคสจริง: 7.29 กม. ขณะที่มิเตอร์ 12.0)
- 🧷 **กันระยะทาง–เวลารถติดเพี้ยนหลังปิด/ย่อแอป** — ระบบจำ "ฐานหลักฐาน" ณ วินาทีที่แอปถูกซ่อน/ปิด
  (ระยะทาง + เวลารถติด + ตำแหน่ง) แล้วเบิกคืนจากฐานนั้นครั้งเดียว → ตัวเลขไม่บวมและไม่หายข้ามรีเฟรช
- 🚫 **ล็อกจอ/ปิดแอป = ไม่นับเวลารถติดเอง** — ไม่มี GPS fix สดใหม่ = ไม่นับต่อ (เดิมนับ 1 วิ/วิ ตลอดช่วงที่ล็อกจอ)
  เคสจริง: ล็อกจอทั้งเที่ยว 10.7 กม. → แอปขึ้น `18:03` แต่มิเตอร์จริง `4:54` → 149 บาท แทน 113
  ของจริงคือ **เบิกคืนเมื่อมีหลักฐานครั้งถัดไป** — จอดจริงก็ได้ครบ · วิ่งจริงก็ไม่ถูกคิดเป็นเวลาจอด
- 🧾 **ยอดที่ "เดา" ไม่ใช่หลักฐาน** (เพิ่ม 15 ก.ย.) — วินาทีที่ระบบนับไปก่อนตอนไม่มี fix (> 15 วิ) ถูกหักออกจาก
  "ยอดที่นับได้จริง" ก่อนตัดสินตอนเบิกคืน — กันเวลารถติดบวมเงียบ ๆ หลังล็อกจอ (เคสจริง: แอป 1:21:32 / อีกเครื่อง 1:12:02)
- 🔁 **ช่วงที่ไม่มี GPS ต้องไม่ถูกล้างทิ้ง** (เพิ่ม 15 ก.ย.) — เดิมถ้าเปิดจอไม่ทันวินาทีแรก (fix ยังไม่นิ่ง/หยาบเกิน 150 ม.)
  ระบบจะ "ล้างช่วง" ทิ้งทันที = ระยะทางช่วงนั้นหายถาวร ตอนนี้เก็บช่วงไว้แล้ว **ลองใหม่ทุก 10 วิ ถึง 20 นาที**
- 📋 **ตัวช่วยวินิจฉัย** — เรียก `window.__gapAudit()` ในคอนโซลได้ทุกเมื่อ: ช่วงที่ค้างอยู่ · จำนวนครั้งที่ลองใหม่
  · เหตุผลล่าสุด · อายุ fix ล่าสุด · จำนวนครั้งที่ปลุก GPS · วินาทีที่ "เดา" ไว้
- ⚙️ **ประเมินเวลารถติดช่วงแอปปิดจาก "ความเร็วล้อหมุนจริงของเที่ยวนี้"** ไม่ใช่ค่าคงที่ 65 กม./ชม. อีกแล้ว
  คิดแบบมิเตอร์: **เวลารถติด = เวลาทั้งช่วง − เวลาที่ล้อหมุน** แล้วเลือกใช้ **ค่าที่มากที่สุด** จาก 2 หลักฐาน
  (① เวลาวิ่งโล่งของช่วงนั้นจาก TomTom · ② ระยะที่วิ่ง ÷ ความเร็วล้อหมุนที่วัดจาก GPS ของผู้ขับคนนี้)
  → ไม่มีข้อมูลเลย = 25% ของช่วง (เทียบเคสจริง: ปิดแอป 13 นาที วิ่ง 5 กม. — เดิมเบิก 8:09 → ใหม่ 1:44)
- 🐌 **ช่วงที่รถ "คลาน" (≤ 6 กม./ชม. แต่ยังขยับ) ถูกหักเวลาด้วยความเร็วคลานจริง** (แก้ 16 ก.ย. — รอบนี้)
  ระยะที่คลานถูกนับเข้า km แล้ว แต่มิเตอร์คิด *เวลาที่คลาน* เป็นเวลารถติด ⇒ ถ้าเอาความเร็ววิ่ง (> 6) ไปหารระยะที่คลาน
  ด้วย จะหักเวลาวิ่งเกินจริง → **เวลารถติดบวมเงียบ ๆ ทุกครั้งที่ล็อกจอในรถติด** แอปจึงสะสม `crawlKm/crawlSec` ตอนจอเปิด
  แล้วคิด `เวลาวิ่ง = ระยะวิ่ง ÷ ความเร็ววิ่ง + ระยะคลาน ÷ ความเร็วคลาน` (คลานถูกเพดานไว้ 25% ของระยะ)
  — พิสูจน์ในชุดทดสอบอัปเดต: ช่วงซ่อน 4 นาทีที่รถคลาน คิดรถติด 146 วิ (เดิม 204 วิ) · ไม่คลานเลย = ตัวเลขเดิมเป๊ะ
- 🚫 **ไม่บวก "เวลารถติดสำรอง 3%" ทับช่วงที่ประเมินได้จากหลักฐานจริงแล้ว** (แก้ 16 ก.ย.) — เดิมบวกให้ทุกช่วง ≥ 2 นาที
  ⇒ ทุกครั้งที่ซ่อนจอคิดเกินเล็กน้อย + สะสมเป็นนาทีต่อเที่ยว · ตอนนี้ใช้ค่าสำรองเฉพาะเมื่อ "ไม่มีหลักฐานเลย" เท่านั้น
- 📉 **ใช้ความเร็วของผู้ขับเองเร็วขึ้น** (เกณฑ์หลักฐาน 60 วิ/0.5 กม. → **25 วิ/0.25 กม.**) — คนที่ล็อกจอบ่อยมีช่วงจอเปิดสั้น ๆ
  เดิมไม่ผ่านเกณฑ์จึงตกไปใช้เวลาวิ่งโล่งของ TomTom (เร็วเกินจริงในเมือง) = เก็บส่วนต่างเป็นรถติด
  · ค่าที่ต่ำกว่า 15 กม./ชม. เชื่อได้เฉพาะเมื่อหลักฐานยาวพอ (≥ 2 นาที · ≥ 1 กม.)
- 🛣️ **TomTom บอก "ทางโล่ง" ไม่เท่ากับ "ไม่มีเวลารถติด"** (แก้ 16 ก.ย.) — TomTom รู้ชนิดถนนแต่ไม่รู้ไฟแดง/ทางแยก/ด่าน
  การใช้เวลาวิ่งโล่งของ TomTom เป็นหลักทุกช่วง (โดยเฉพาะล็อกจอสั้น ๆ หลายสิบครั้งต่อเที่ยว) ทำให้ส่วนต่างถูกนับเป็นรถติดทุกครั้ง
  เคสจริง: เปิดจอตลอด `1:12:02` (มิเตอร์ `1:10:37`) แต่ **รอบที่ล็อกจอบ้างขึ้น `1:21:32`** → ตอนนี้อิงความเร็วล้อหมุนจริงก่อน
- 🚦 **ล็อกจอที่มีทั้ง "จอด" และ "วิ่งสั้น ๆ"** (แก้ 16 ก.ย.) — เดิมถ้าความเร็วเฉลี่ยทั้งช่วง ≤ 6 กม./ชม. ระบบเหมาเป็น
  "จอดทั้งช่วง" → นับเวลาวิ่งเป็นรถติด **และ** ทิ้งระยะทางที่วิ่งจริงด้วย ตอนนี้ขยับไกลเกินกรอบความคลาดเคลื่อนของ fix
  = เข้าสู่เส้นทาง "วิ่ง" (คิดทั้งเวลาและระยะ) · ยังเหมาเป็น "จอด" เมื่อการขยับอธิบายได้ด้วย GPS ลอย
- 🐞 **ตัดปลายจุดจอดที่ยังไม่มีหลักฐาน** (แก้ 16 ก.ย.) — ตอนจอเปิด ระบบนับเวลารถติดได้ถึง *fix ล่าสุดที่ยืนยันว่าจอด*
  (ไม่ใช่ถึงวินาทีปัจจุบัน) — ไม่กินเวลาช่วงที่รถออกตัวแล้ว · ค่าผ่อนผันเรียนรู้จากช่วงห่างจริงของ GPS เครื่องนั้น
- 📋 **ดูเหตุผลการเบิกคืนได้** — `window.__gapAudit()` มี `lastModel` บอกว่าช่วงซ่อนรอบล่าสุดหักเวลาวิ่งจากหลักฐานไหน (TomTom/ความเร็วล้อหมุน) เท่าไร
- 🧾 **การ์ดหลักฐานการเบิกคืน** — ในหน้าสรุปค่าโดยสารมีหัวข้อบอกช่วงที่แอปถูกปิดและยอดที่เบิกไป เพื่อตรวจย้อนหลังได้
- 🎯 **ปรับเทียบมิเตอร์จริง** — กรอก กม.+ราคา จากมิเตอร์ตอนจบเที่ยว แล้วหน้าประวัติสรุปส่วนต่างเฉลี่ยเป็น %
  พร้อมบอกว่าแอปคิดสูงกว่าหรือต่ำกว่ามิเตอร์จริง (เทียบเฉพาะส่วนมิเตอร์ — ไม่รวมค่าทางด่วน)
- ⏳ **จำกัดเวลาจอดที่เบิกหลังปิดแอปได้** — กันค่าโดยสารบวมถ้าลืมจบเที่ยวข้ามคืน

- **ยืนยันสำเร็จแล้วผ่อนผัน 2 นาที** สำหรับงานหลายขั้นตอนติดกัน (กันพิมพ์รหัสซ้ำรัว ๆ)
- **ออฟไลน์:** ตรวจรหัสไม่ได้ → ระบบ **ถามยืนยันจากผู้ใช้** ไม่ปล่อยผ่านเงียบ ๆ และไม่ล็อกการทำงานตอนเน็ตหลุด
- ธีม/การตั้งค่าที่แก้บ่อย (เต็มจอ · สั่น · เสียง · ประเภทรถ) **ไม่ต้องยืนยัน** — ไม่เกี่ยวกับความปลอดภัยของบัญชี
- รายการทั้งหมด + กติกาห้ามละเมิดอยู่ที่ [`SECURITY.md` หัวข้อ 9](SECURITY.md)

อ่านเอกสารสมาชิกได้ (มีรหัสผ่านและเบอร์โทร) · คิวรีรายชื่อได้ · เขียนลบเที่ยวในประวัติรายได้ได้ ·
ลบร่องรอยในประวัติการใช้งานได้ · สร้างคอลเลกชันอะไรก็ได้ (ใช้โปรเจกต์เป็นที่ฝากไฟล์)

> ⚠️ ช่องนี้ทำให้ **ด่านยืนยันตัวตน 7 จุดในแอปมีผลไม่เต็มที่** — คนที่รู้รหัสโปรเจกต์ยิง API ตรงได้เลย
> โดยไม่ผ่านตัวแอป จึงควรปิดเป็นลำดับแรก

### ✅ วิธีปิด (รายละเอียดใน [`SECURITY.md`](SECURITY.md))

1. คัดลอก [`firestore.rules`](firestore.rules) → Firebase Console → Firestore Database → Rules → **Publish**
2. รัน `tests/security-check.ps1` ซ้ำ → ต้องขึ้น **LOCKED ทั้ง 7 ข้อ**
3. ถ้าต้องการปิดระดับ "ใครอ่านได้" ด้วย เปิด **App Check (reCAPTCHA v3)**:
   Firebase Console → App Check → ลงทะเบียนเว็บแอป แล้วใส่ site key ที่ `APP_CHECK_SITE_KEY` ใน `index.html`
   → กด Enforce ที่ Firestore (ค่าเริ่มต้นคือ **ปิด** — ไม่กระทบพฤติกรรมเดิมของแอป)
4. **ปิดให้สนิทจริง** → ดู [`FIREBASE-AUTH.md`](FIREBASE-AUTH.md) (Firebase Auth + Custom Token ผ่าน Cloud Functions)
   แล้วใช้ [`firestore-auth.rules`](firestore-auth.rules) แทนไฟล์แรก — กติกาจะเช็ก "เจ้าของบัญชี" ได้จริง

### 🧭 ข้อจำกัดที่ต้องรู้

- แอปนี้ **ไม่ได้ใช้ Firebase Authentication** (ล็อกอินด้วย Username/รหัสผ่านของตัวเอง) จึงแยกไม่ออกว่า
  คำขอมาจาก "แอปของเรา" หรือ "สคริปต์ของคนนอก" เพราะทั้งคู่ไม่มีตัวตน → กติกาชุดนี้จึง **จำกัดรูปแบบ+กันการลบ**
  ไม่ใช่การปิดประตูสนิท · การปิดจริงต้องพึ่ง **App Check** หรือย้ายไป **Firebase Auth**
- คีย์ Firebase ในไฟล์เป็น **คีย์ฝั่งเว็บ** (ใช้ระบุโปรเจกต์ ไม่ใช่ความลับ) — ความปลอดภัยจริงอยู่ที่กติกา
- ห้าม commit รหัสผ่านจริง ข้อมูลผู้โดยสาร หรือข้อมูลส่วนตัวลง repository
- คีย์ API ของ TomTom มีโควตาฟรีต่อวัน แอปมีการนับและเตือนในเครื่องเมื่อใกล้เต็ม
- **เพื่อประหยัดโควตา TomTom:** กระเบื้องจราจร (Traffic Flow) ถูกถอดออกจาก Mini Map แล้ว — แผนที่ใช้กระเบื้อง **OpenStreetMap** (ฟรี) ทั้งหมด ส่วน TomTom ถูกเรียกเมื่อ **คำนวณเส้นทาง** เท่านั้น
